# Hexo / Hugo / Astro 技术栈对比

> 2026-10-31 实测于本机（Apple silicon，macOS 26，Node 26.13.0）。所有基准数字都是我在 `/tmp` 里现搭现测的，不是抄的。
> 语料：500 篇 / 2000 篇同构 Markdown（标题 + 列表 + 代码块 + 行内/行间公式 + 三节正文）。

---

## 0. 一句话定位

| | 本质是什么 |
|---|---|
| **Hexo** | 「WordPress 的静态版」：Node 进程里维护一个内存数据库，插件管线处理内容，模板引擎套壳输出。 |
| **Hugo** | 「编译器」：一个 Go 二进制把内容树编译成站点，无运行时、无依赖、并行渲染。 |
| **Astro** | 「前端框架的静态出口」：Vite + 组件树，默认零 JS，需要交互的地方才挂载 island。 |

这三种定位决定了它们的全部差异——后面每一条都是这三句话的推论。

---

## 1. 架构与渲染机制

### Hexo

```
source/*.md
   │  front-matter 解析（js-yaml）
   ▼
[ Processor 管线 ]  →  Markdown 渲染器插件（marked / markdown-it / katex）
   ▼
[ 内存数据库 Warehouse ]  ← 关键：全站内容在 Node 堆里建索引
   ▼
[ Generator 管线 ]  →  index / archive / category / tag / feed 各生成器并行产出"路由"
   ▼
[ 主题渲染 ]  →  EJS 递归渲染模板 + Stylus/Sass 编译 + 静态资源拷贝
   ▼
public/
```

- 核心是 **`hexo` 这个 npm 包 + 一堆 `hexo-xxx` 插件**，所有能力都靠插件组合：渲染（renderer）、生成（generator）、部署（deployer）、过滤（filter）、标签（tag）。
- 模板层是 **EJS/Less/Stylus/Pug**：字符串模板 + 局部模板，没有组件树概念。改布局 = 改模板文件。
- 内容进内存数据库这一步是速度瓶颈的来源，也是 `hexo clean` 存在的理由。

### Hugo

```
content/*.md
   │  front-matter（YAML/TOML/JSON）
   ▼
[ 内容树 + 分类法(taxonomy) 索引 ]   ← Go 里构建，goroutine 并行
   ▼
[ 模板查找 ]  layouts/{_default,partials,shortcodes,主题名}/...
   ▼
[ 资源管线 Hugo Pipes ]  →  Sass/PostCSS、JS bundling(esbuild)、图片 resize/WebP/AVIF
   ▼
[ 并行写盘 ]
   ▼
public/
```

- **没有插件系统**（作者刻意的设计）。要新能力：写 shortcode、partial、或用内置的 `resources` 管线。这既是优点（不会因为插件停更而坏）也是缺点（稍微特殊的需求得自己写模板）。
- 模板是 **Go 的 `html/template`**：`{{ range .Pages }}` 这种语法，逻辑表达力强但和 JS 生态割裂。
- 图片处理内置且是杀手级：`{{ $img := resources.Get "a.jpg" }}{{ $img.Resize "800x webp" }}`，不需要 gulp/sharp 之类的额外链路。

### Astro

```
src/content/blog/*.md   ← content collection（Zod schema 校验 front-matter）
   │
   ▼
[ Vite 构建图 ]  →  .astro 组件（前端部分跑在构建期）+ Integration 钩子
   ▼
[ Markdown 管线 ]  remark → rehype（插件化，KaTeX 在这里接）
   ▼
[ 输出 ]  静态 HTML + 按需水合的 island（React/Vue/Svelte/Solid 都能挂）
```

- 核心是 **Vite + `.astro` 单文件组件**（HTML 语法 + 顶部 `---` 里的构建期 JS/TS）。
- **Content Collections**：给 front-matter 定义 Zod schema，构建期校验——字段写错直接报错，这是三者里唯一有「内容类型安全」的。
- 默认零客户端 JS；需要交互时才 `client:load` 挂一个 island。这让它的产物天然比另两家轻（前提是别乱挂组件）。

## 2. 实测构建性能（同机、同语料）

| 生成器 | 500 篇 | 2000 篇 | 产出 HTML 数 |
|---|---|---|---|
| **Hugo 0.169**（单二进制，`hugo` 直接跑） | **0.24 s**（二次 0.20 s） | **1.02 s**（二次 0.86 s） | 523 / 2523 |
| **Hexo 8.0**（`npx hexo g`） | 1.54 s（内部 668 ms） | 4.11 s | 874 / 约 3300 |
| **Astro 7.4**（`npx astro build`） | 1.72 s（内部 1.19 s） | 3.41 s | 501 / 2001 |

读数说明（别直接拿去当结论）：

- Hexo / Astro 的 wall time 含 Node 冷启动（约 0.5–0.9 s），所以更公平的是「内部耗时」那列。
- **Hexo 的产出页数明显多**：它默认额外生成 archives / tags / categories / 分页，同样内容比另两家多写 60%+ 文件。按「每页成本」算，Hugo 约 0.4 ms/页，Hexo 约 0.7 ms/页，Astro 约 2.4 ms/页（Astro 的差异主要来自 Vite 打包阶段，与页数是两条曲线）。
- 500 篇时 Hugo 已快 4–6 倍；2000 篇时 Hexo 增长到 4.1 s 而 Hugo 1.0 s，**规模越大差距越明显**——Hugo 的 goroutine 并行是线性摊薄的，Node 那两家受单线程 + 内存数据库拖累。
- 但说实话：**你现在的博客只有 3 篇。三者在你的量级上都是「按一下回车就完事」**，这条指标对你的决策权重应该排最后。

## 3. 依赖与可复现性（长期维护的关键）

| | 依赖形态 | 三年后还能构建吗 | 实际踩过的坑 |
|---|---|---|---|
| Hexo | `package.json` 依赖树（本项目实测 **243 个包**） | 大概率能，但要看 Node 版本 | npm 11 拦 `hexo-util` 的 postinstall；残留 pnpm 结构的 `node_modules` 让 `npm install` 崩在 `Link.matches`；Hexo 8 要求 Node ≥ 20.19，插件跟进慢就会卡住 |
| Hugo | **0 个依赖**，一个 90 MB 二进制 | 几乎一定——把二进制版本钉在 CI 里就行 | 几乎没有依赖类故障；代价是模板报错信息偏「Go 风格」 |
| Astro | 依赖树（本项目实测 **185 个包**） | 能，但需跟大版本迁移 | 今天我亲历：Astro 7 把 content config 从 default export 改成 `export const collections = {...}`，我照旧写法连报两次错才发现——**这就是快速迭代的真实成本** |

这条是我认为**权重最高**的一条。静态博客的常见死法不是「不好看」，而是「半年后 `npm i` 装不上、Node 升级后构建炸了、然后就再也没更新过」。你的旧站就是活生生的例子——不过它死在 force push 上，属于另一类事故。

## 4. 内容模型

| | front-matter | 校验 | 分类法 | 特殊语法 |
|---|---|---|---|---|
| Hexo | YAML，字段自由 | 无（写错就是渲染出空值） | 内置 categories/tags，但只生成列表页 | 标签插件 `{% codeblock %}`、`{% note %}` 等 |
| Hugo | YAML/TOML/JSON | 无 schema，但有 `archetypes` 模板约束新建 | **taxonomy 是可控的**：可自定义任意分类维度（series/author/topic） | shortcode `{{< figure >}}` 可自定义 |
| Astro | YAML front-matter | **Zod schema 强校验**，构建期报错 | 无内置，自己写页面或用集成 | 组件直接写，MDX 可选 |

Astro 的 schema 校验在「多人协作 / 内容多了以后」是实打实的优势；单人写博客时，它更像是「多一层配置负担」。

## 5. 主题机制（和你「换主题」的诉求直接相关）

| | 主题是什么 | 换主题操作 | 深度定制 |
|---|---|---|---|
| Hexo | 主题目录 + 一份 `_config.<theme>.yml`（几百个开关） | 换 `theme:` 值 + 装包 + 改配置 | 改 EJS 模板，可接受但耦合 |
| Hugo | 主题目录（模板集合）+ 主题自己的配置段 | 换主题 = 换一个 `themes/` 目录，配置要重写 | 用 `layouts/` 覆盖主题的部分模板（**覆盖机制优雅**，只改想改的那块） |
| Astro | 主题 = 一个完整项目 | **等于换一个工程**，内容要重接 | 自由，因为一切都是你的代码 |

Hugo 的「覆盖式定制」值得单独夸一句：你只需要在项目里放 `layouts/_default/single.html` 就能盖掉主题的同名模板，不用 fork 整个主题——**换主题时这些覆盖文件会失效，但不影响你换主题本身**。

## 6. 你的具体需求，三家各怎么满足

| 需求 | Hexo | Hugo | Astro |
|---|---|---|---|
| KaTeX 公式（你那篇物理笔记） | `hexo-renderer-katex` 或 markdown-it + katex 插件 | 原生 `math` 支持（MathJax/KaTeX 配置项） | `remark-math` + `rehype-katex` |
| 代码高亮 | highlight.js / prismjs 插件 | 内置 Chroma（服务端高亮，产物无 JS） | Shiki（构建期高亮） |
| 评论（giscus/waline） | 主题配置项 | 主题配置项 / partial | 自己写组件 |
| 站内搜索 | `hexo-generator-searchdb`（本地 JSON） | 主题常内置（Fuse.js 或 Pagefind） | Pagefind 集成 |
| 图片处理 | 靠插件或手动 | **内置** resize/WebP/AVIF | `astro:assets` 内置 |
| sitemap / RSS | 两个插件 | 内置 `sitemap.xml`、`rss.xml` | 两个官方集成 |
| 中文生态文档 | **最好** | 中等 | 少 |

**顺手发现一件事**：你现在的站从 `cdn.jsdelivr.net` 和 `cdnjs.cloudflare.com` 拉了至少 6 个外部资源（jQuery、KaTeX、highlight.js、lightgallery、justifiedGallery、cookieconsent）。Icarus 的设计依赖 CDN，意味着**首屏能不能出来取决于境外 CDN 通不通**。Hugo 和 Astro 都可以把这些资源打进自己的 `public/`，属于「顺手就能修好的隐患」。

## 7. 决策矩阵（按你的实际诉求打分，5 分制）

| 诉求 | Hexo | Hugo | Astro |
|---|---|---|---|
| 换主题的自由度与多样性 | **5** | 4 | 2 |
| 长期不用管 | 3 | **5** | 3 |
| 构建速度 | 3 | **5** | 4 |
| 产物轻量 | 3 | 4 | **5** |
| 定制上限 | 3 | 3 | **5** |
| 学习成本低 | **5** | 3 | 3 |
| 中文资料 | **5** | 3 | 2 |
| **加权（按你「想换主题 + 内容少 + 想长期不折腾」）** | **4.3** | **4.2** | 2.7 |

两家咬得很紧，差别在取向：**Hexo 赢在「主题多、改配置就行」；Hugo 赢在「装完就不用再管」**。Astro 在「以换主题为初衷」的前提下直接出局。

---

## 8. 结论

- 如果你打算**频繁换主题、想开箱就有评论/搜索/目录** → Hexo 8 + Butterfly/Fluid。缺点是得接受 npm 依赖树的脆弱性，并且每次大版本升级要陪着折腾。
- 如果你觉得**「三年后再回来也能 `git pull && build` 成功」比主题数量重要** → Hugo + Stack/PaperMod。构建 4 倍快、零依赖、图片管线内置，代价是深度定制要写 Go 模板。
- Astro 只在一种情况值得：你准备把它当**前端作品**来做，愿意为每个部件写代码。以「换主题」为起点，方向是反的。

我的排序没变：**Hexo 8 优先，Hugo 次席且差距很小**。区别只在于你更怕「主题不够挑」还是更怕「半年后装不上依赖」。
