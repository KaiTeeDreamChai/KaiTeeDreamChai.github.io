# 博客重建方案对比

> 写于 2026-10-31。现状：Hexo 7.3.0 + Icarus，只发布编译产物，源码已丢失；真实内容仅 1 篇物理笔记 + 1 个 about 页；Pages 走 legacy 分支部署，14 天 0 访问。
> 目标：换主题、以后长期不再返工。

---

## 0. 先看清约束（这决定了「什么才值得比较」）

| 约束 | 事实 | 对方案的影响 |
|---|---|---|
| 源码 | 不在 GitHub，本机也没有；仓库历史被 force push 覆盖到只剩一个 `placeholder` | 任何方案都要**新建工程**，不存在「原地改主题」 |
| 内容量 | 3 篇（含 1 篇模板占位、1 篇空文），有效内容 1 篇 + about | **迁移成本几乎为零**，选型不必被旧包袱绑架 |
| 部署 | `build_type: legacy`，master 根目录直发 | 建议改成 Actions 构建，源码与产物分离 |
| 基础设施 | robots / sitemap / feed / 404 全缺 | 新方案应顺手补齐 |
| 现有流量 | 0 | 不需要保留旧 URL 的 SEO 权重，但仍建议保持路径风格一致 |

结论：**这不是一道「迁移」题，而是一道「从零选技术栈」的题**。所以真正的比较维度是——主题生态、构建/维护成本、长期稳定性、折腾上限。

---

## 1. 三套候选总览

| 维度 | A. Hexo 8 | B. Hugo | C. Astro |
|---|---|---|---|
| 最新版 | 8.1.2（2026-05） | v0.169.0（2026-10） | 7.4.4 |
| 运行环境 | Node ≥ 20.19 + npm 依赖树 | 单个二进制，无运行时依赖 | Node + npm 依赖树 |
| 本机构建速度 | 实测 11 文件 **79 ms**；百篇级仍在秒级 | 千篇级毫秒~秒级，最快 | 与 Hexo 同量级，首屏最轻 |
| 主题生态 | **最丰富**（中文社区主场） | 丰富、风格偏简洁英式 | 少但精，偏「作品感」 |
| 换主题成本 | 改 `_config.<theme>.yml` + 装包 | 换 `themes/` 目录 + 改 config | 换 template 集成，改动较大 |
| 中文资料 | **最多**（Butterfly/Fluid 文档齐全） | 中等 | 少 |
| 维护风险 | 依赖树较脆（npm 11 已在拦 `hexo-util` 的 postinstall） | **最低**（无依赖树） | 中（Astro 大版本迭代快） |
| KaTeX 公式 | `hexo-renderer-katex`，配置即用 | 原生 `math` 支持 | 需装 `remark-math`+`rehype-katex` |
| 折腾上限 | 中（模板 EJS/Stylus，可改但不优雅） | 中 | **高**（组件化，能写自己的布局） |
| 适合谁 | 想要「主题多、开箱功能全」 | 想要「装上就不再管」 | 想要「自己的站长得跟别人不一样」 |

## 2. 逐项拆解

### A. Hexo 8 + 新主题（延续现状，换皮）

**主题候选（★ 为 GitHub star，均为 2026 年仍在更新）**

| 主题 | ★ | 特点 | 适合你吗 |
|---|---|---|---|
| Butterfly 5.7 | 8.4k | 功能最全：搜索、评论、封面轮播、字数统计、PJAX，中文文档极全 | ✅ 想少折腾、功能齐 |
| Fluid 1.9.9 | 8.2k | 克制、留白多、Material 风，配置项比 Butterfly 少一半 | ✅ 偏「安静阅读」 |
| Redefine 2.9 | 2.0k | 现代卡片风、渐变、动效多，颜值派 | ✅ 想要「好看」优先 |
| Stellar 2.0 | 2.1k | 结构化强、适合做「知识库/文档站」混排 | 若博客兼笔记库 |

- **迁移工作量**：新建 Hexo 8 工程 → 抓回旧文章 → 配主题 → 写 Actions。我这边**半天内可交付**。
- **风险**：Hexo 生态整体偏老，插件停更普遍；Node 26 + npm 11 需要加 `allow-scripts` 白名单（已踩通）。Hexo 8 要求 Node ≥ 20.19，CI 需锁 Node 22。
- **代价**：以后每换一次主题，都是一次 config 重写（可接受，毕竟主题多）。

### B. Hugo + Stack / PaperMod / Blowfish（最省心）

| 主题 | ★ | 特点 |
|---|---|---|
| PaperMod 14.0k | 极致简洁，纯文字派，几乎零配置 |
| Stack 6.5k | 卡片 + 侧栏，中文用户多，观感接近 Fly 系 |
| Blowfish 2.9k | 配置项极多，Tailwind 驱动，可玩性高 |
| FixIt 1.1k | 中文社区维护，功能对齐 Butterfly |

- **迁移工作量**：把 Markdown 搬到 `content/posts/`，front-matter 基本兼容（`title/date/tags/categories`）。1 篇 + about，**一小时内**。
- **优势**：增量构建快、无 node 依赖地狱、部署只需把 `hugo` 二进制丢进 Actions；十年后还能构建。
- **劣势**：中文主题的「开箱感」不如 Hexo（评论、搜索、字数统计要自己接）；主题定制语言是 Go template，改起来不如 EJS 直观。

### C. Astro（Fuwari / Astro Paper）

| 主题 | ★ | 特点 |
|---|---|---|
| Fuwari 5.1k | 二次元/柔和风，动效与配色最好看 |
| Astro Paper 5.2k | 极简、Lighthouse 满分常客 |

- **迁移工作量**：内容能搬，但**目录结构、资源引用、组件都要重接**。以你的内容量，纯手搬也就 2 小时，但后续每写一篇都更「工程化」。
- **优势**：产物最轻（只发 HTML+少量 JS），可做交互组件，成长性最好。
- **劣势**：没有「改两行配置就换皮」的体验；主题其实等于一套代码，换主题 ≈ 换个项目。这与你的原始诉求（「更换主题之类」）方向相反。

## 3. 三个容易被忽略的决策点

1. **源码要进 Git，且不要 force push。** 旧站翻车的根因就是 `hexo-deployer-git` 每次强推覆盖历史。改法：`master` 存源码，Pages 改成 **GitHub Actions** 构建发布 —— 以后换主题、写文章都是可回滚的 commit。
2. **URL 风格先定死。** 旧站是 `/YYYY/MM/DD/slug/`。新站无论用哪套，都建议保持同样 permalink，未来搬去自定义域名时不会断链。
3. **一次性把「基础设施」补齐。** sitemap、RSS、404、robots、OG 图 —— 这些在 Hexo/Hugo 里都是一个插件或一行配置，但漏了就是「博客像没被搜索引擎看见过」，和你现在的状态一样。

---

## 4. 我的建议

**首选 A（Hexo 8 + Butterfly 或 Fluid），并把部署换成 Actions。**

理由，按权重排：

1. 你的诉求是「换主题之类」——Hexo 的中文主题生态是三者里唯一能「改配置就换一张脸」的，而且功能开箱齐全（搜索/评论/目录/字数）。选 Hugo 或 Astro 会把「换主题」变成「换工程」。
2. 你的内容量小，A 的迁移成本最低，且我能在一次会话里交付可上线版本，你能立刻看到效果再决定要不要继续折腾。
3. 你已经有 Node 26 环境并跑通了全链路，A 是唯一「装完就能用」的路径。

**如果更看重「以后别再管它」→ 选 B（Hugo + Stack）。** 构建快一个数量级、依赖树不存在、十年后仍能构建；代价是主题定制和中文生态略逊。

**C（Astro）只在一种情况下值得选**：你打算把这个站当成「前端作品」，愿意为每个组件写代码。以「换主题」为初衷的话，它是反方向。

---

## 5. 决定之后的第一步（无论选哪个）

1. 从线上抓回 2 份真实内容（`about` 页、`带电粒子在匀强电场中的运动`）——我已验证可解析，含 KaTeX 公式。
2. 新工程落在 `~/Documents/deepseek-harness/Blog`，`git init` 后推到 `KaiTeeDreamChai.github.io` 的 `master`（源码）。
3. 加 `.github/workflows/deploy.yml`：Node 22 / Hugo 版本锁定 → 构建 → `actions/deploy-pages` 发布。
4. Pages 设置从 `legacy (master /)` 切到 `GitHub Actions`。
5. 本地 `hexo s` 验收 → 推一次 → 打开线上核对，再补 sitemap/RSS/404。

> 需要的话，我可以先只做第 1 步（把旧内容抓成本地 Markdown 存好），不动仓库、不动 Pages —— 这样你后面无论选哪套，素材都是现成的。
